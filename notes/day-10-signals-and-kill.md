## 1. The Core Mental Model: Real-World Analogy
Imagine working at your office desk:
* **`SIGTERM` (Signal 15 - Polite Request)**: A security officer walks up and says, *"The building closes in 15 minutes. Please save your work, commit your code, turn off your monitors, and exit."* You have time to cleanly finish what you are doing.
* **`SIGINT` (Signal 2 - Immediate Cancellation / `Ctrl+C`)**: A colleague runs in and shouts, *"Cancel that print job immediately!"* You stop your current calculation right away.
* **`SIGHUP` (Signal 1 - Hangup / Reload)**: The boss hands you an updated company handbook through the window: *"Here is the new company policy; re-read your settings without leaving your desk!"*
* **`SIGKILL` (Signal 9 - Instant Annihilation)**: A wrecking ball smashes through the wall and obliterates the entire room in a microsecond. You get **zero seconds** to save your work, zero opportunity to close files, and no chance to say goodbye. The operating system kernel simply reclaims your memory instantly.

## 2. Low-Level Kernel Architecture: How Signals Work Under the Hood

In `struct task_struct`, the Linux kernel maintains bitmasks representing pending and blocked signals:

```c
struct sigpending {
    struct list_head list;
    sigset_t signal; /* 64-bit bitmask of pending signals */
};
```

### The Delivery Mechanism:
1. **Asynchronous Interrupt**: A signal is generated by hardware (e.g. division by zero triggering `SIGFPE`, MMU page fault triggering `SIGSEGV`) or software (`kill()` syscall, terminal driver `Ctrl+C`).
2. **Pending Bit Set**: The kernel sets the corresponding bit in the target process's `pending.signal` bitmask.
3. **Context Transition Check**: The kernel does **not** interrupt the CPU in the middle of executing an assembly instruction. Instead, signal delivery is evaluated whenever the CPU transitions from **Kernel Space back to Userspace** (such as returning from any system call or timer interrupt).
4. **Stack Trampoline & `sigreturn()`**:
   * If a custom handler is registered via `sigaction()`, the kernel creates a special frame (`sigframe`) on the user-space stack.
   * It writes the return address pointing to a small kernel stub (`__kernel_sigreturn`).
   * When the user's signal handler completes, it returns into this stub, which issues the `sigreturn()` syscall.
   * `sigreturn()` restores the original CPU registers and instruction pointer so normal execution can resume seamlessly.

## 3. Comprehensive POSIX Signal Reference

| Number | Macro Name | Default Action | Trappable? | Typical Origin / Purpose |
| :---: | :--- | :--- | :---: | :--- |
| **`1`** | **`SIGHUP`** | Terminate | Yes | Terminal disconnection ("Hangup"). Modern daemons use this to trigger configuration reloads without restarting. |
| **`2`** | **`SIGINT`** | Terminate | Yes | Sent by the terminal driver when the user presses `Ctrl+C`. |
| **`3`** | **`SIGQUIT`** | Core Dump | Yes | Sent by `Ctrl+\`. Requests immediate termination with a memory core dump for debugging. |
| **`9`** | **`SIGKILL`** | **Terminate Instantly** | **NO** | Kernel forcefully terminates the process. Cannot be caught, blocked, or ignored. |
| **`11`** | **`SIGSEGV`** | Core Dump | Yes | Segmentation fault: Process attempted to read/write unmapped or protected virtual memory. |
| **`13`** | **`SIGPIPE`** | Terminate | Yes | Broken pipe: Process attempted to write to a pipe or socket with no active reader. |
| **`14`** | **`SIGALRM`** | Terminate | Yes | Real-time timer expiration set by `alarm()` syscall. |
| **`15`** | **`SIGTERM`** | Terminate | Yes | Default polite termination signal sent by `kill <PID>` and container runtimes (Docker, Kubernetes). |
| **`17`** | **`SIGCHLD`** | Ignore | Yes | Sent to the parent process whenever a child process terminates, stops, or resumes. |
| **`19`** | **`SIGSTOP`** | **Stop / Pause** | **NO** | Unconditionally freezes the process. Cannot be caught or blocked. |
| **`18`** | **`SIGCONT`** | Continue | Yes | Resumes a process paused by `SIGSTOP` or `SIGTSTP`. |

## 4. Async-Signal-Safety: The Critical C/C++ Systems Engineering Rule

A signal handler can interrupt a thread at **any arbitrary line of assembly code**, including while inside a critical mutex or memory allocation routine.

### The Deadlock Hazard:
Suppose your main thread is executing `malloc(1024)`. Inside `malloc()`, the standard C library acquires an internal global memory pool lock.
Right at that moment, a signal arrives! The OS pauses the main thread and runs your custom signal handler.
If your signal handler calls `printf("Got signal!\n")` or `malloc()`:
1. `printf` internally calls `malloc` or locks `stdout`.
2. `malloc` attempts to acquire the internal memory pool lock.
3. But that lock is **already held** by the paused main thread on the exact same CPU core!
4. **Instant Permanent Deadlock**: The process hangs forever!

### POSIX Async-Signal-Safe Functions:
Only a strictly designated list of system calls are guaranteed to be safe inside signal handlers (e.g. `write()`, `_exit()`, `sigaction()`).
In modern systems engineering:
* **Best Practice**: The signal handler should do nothing except set a flag:
  ```c
  static volatile sig_atomic_t g_shutdown_requested = 0;
  void handle_sigterm(int sig) {
      g_shutdown_requested = 1;
  }
  ```
  The main event loop checks `g_shutdown_requested` on each tick and initiates a clean, orderly shutdown in normal userspace context!

## 5. Real-World Production War Story: The Kubernetes 30-Second Pod Termination Race

### The Incident:
An e-commerce payments microservice running on Kubernetes experienced corrupted transactions and missing order confirmations during automated rolling deployments. Customers were charged, but their shopping carts still showed "Checkout Pending", triggering thousands of angry support tickets.

### Root Cause Analysis:
When Kubernetes deploys a new container version:
1. It sends **`SIGTERM` (15)** to the existing Pod's container process (PID 1).
2. It simultaneously removes the Pod from the Service endpoint routing table.
3. It starts a countdown: `terminationGracePeriodSeconds` (default: 30 seconds).
4. If the container has not exited after 30 seconds, Kubernetes sends **`SIGKILL` (9)**.

In this microservice:
* The developers had **not registered a `SIGTERM` handler**!
* In Node.js, Python, and Go, if an application runs as PID 1 in a Docker container without a signal handler, the default Linux kernel behavior for PID 1 is to **ignore unhandled signals**!
* Because `SIGTERM` was ignored, the application continued accepting and processing payments.
* Exactly 30 seconds later, Kubernetes delivered `SIGKILL`!
* The application was instantly incinerated mid-transaction. Database connection pools were abruptly severed without committing or rolling back in-flight transactions, leaving payment gateway states desynchronized.

### Resolution:
1. Implemented a robust `SIGTERM` trap in the application.
2. Upon receiving `SIGTERM`:
   - Stopped accepting new incoming HTTP connections (`server.close()`).
   - Allowed up to 15 seconds for active in-flight payment requests to complete.
   - Flushed all distributed tracing buffers and closed database connection pools.
   - Exited cleanly with status code `0`.
3. Pod terminations dropped from 30-second timeouts to 2.4-second clean shutdowns with zero dropped transactions.

## 6. Staff-Level Technical Interview Deep-Dives

### Question 1: Why can `SIGKILL` (9) and `SIGSTOP` (19) NEVER be caught or ignored?
**Exhaustive Answer**:
* This is a fundamental design invariant of the POSIX security and administration model.
* The operating system administrator (root) must possess an absolute, infallible mechanism to reclaim physical hardware resources, terminate rogue or malicious infinite loops, and halt unresponsive processes.
* If a buggy or malicious process could catch or mask `SIGKILL`, it could hold system RAM, locks, or network ports hostage indefinitely, forcing a complete hard reboot of the physical server.
* The Linux kernel enforces this directly in `kernel/signal.c`: if the signal number is `SIGKILL` or `SIGSTOP`, the kernel bypasses all user handler lookups and forces direct action immediately.

### Question 2: What is the difference between `kill()` and `tgkill()` system calls?
**Exhaustive Answer**:
* `kill(pid, sig)` delivers a signal to an entire Process (Thread Group). Any individual thread within that process that does not have the signal blocked may handle it.
* `tgkill(tgid, tid, sig)` specifically directs a signal to a **single designated thread (`tid`)** within a specific thread group (`tgid`). This syscall is used by thread runtimes (like `pthread_kill` and JVM debuggers) to interrupt a specific worker thread without disturbing other sibling threads.
